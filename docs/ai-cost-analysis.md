# WearWise AI Cost Analysis

**Date:** 2026-09-14
**Scope:** `wearwise-ai/src/wearwise_ai/application`, `models/`, `workers/run_worker.py`, and the job fan-out in `wearwise-api/app/Modules/Ai/Services/AiJobService.php`
**Trigger:** ~$0.50 observed for a 5-image upload; OpenAI Responses log showing 3 model calls per item.

---

## 1. Executive summary

A single wardrobe item upload currently costs **~$0.11**, so 5 images cost **~$0.57**. This matches the reported $0.50.

The cost splits into two independent problems:

| Bucket | Per item | Per 5 items | Share |
|---|---|---|---|
| 3 × `gpt-5` vision calls (classify, colour, attributes) | ~$0.044 | ~$0.22 | 38% |
| 1 × `gpt-image-1` wardrobe visual, medium quality | ~$0.070 | ~$0.35 | 62% |
| **Total** | **~$0.114** | **~$0.57** | |

The three text calls are the ones visible in the attached log (3 rows repeating per item). The image generation call is the larger cost and does not appear in the Responses log at all — it goes through the Images API, which is why the log undercounts the true spend.

**Realistic target after the changes in §5: ~$0.006/item (~$0.03 per 5 images) — a 94% reduction**, without dropping any user-visible feature.

---

## 2. Current architecture

Upload → `background_removal` (BiRefNet, self-hosted, $0) → on completion the Laravel service fans out **5 follow-up jobs**:

`AiJobService.php:839-843`

```
colour_extraction              → OpenAI gpt-5   vision   ← paid
embedding_generation           → SigLIP local            ← free
clothing_classification        → OpenAI gpt-5   vision   ← paid
attribute_extraction           → OpenAI gpt-5   vision   ← paid
wardrobe_item_visual_generation→ OpenAI gpt-image-1      ← paid, most expensive
```

Each of the three vision jobs independently:
1. re-downloads the same background-removed WebP,
2. base64-encodes it into a `data:` URL,
3. sends it to `gpt-5` with `detail: "high"`,
4. asks for a small strict-JSON object back.

**The same image is uploaded to OpenAI three times per item, and three separate reasoning passes run over it.**

## 4. Weak points

Ordered by cost impact.

### W1 — `gpt-image-1` at medium quality for every uploaded item (~62% of spend)

`application/wardrobe_item_visual_generation_service.py:9`, `models/openai_image.py:117-120`

```python
size: str = "1024x1024"
quality: str = "medium"     # ~$0.07 per image
```

Every item that has a name/category/subcategory gets a "clean catalog image" regenerated by `gpt-image-1`. This is the single most expensive operation in the product, and it is triggered **automatically on upload**, not on user request.

Worse: the input to this call is the *already background-removed, already cleaned* BiRefNet output. The pipeline pays a premium generative model to re-render an image it has already cleaned deterministically.

### W2 — Frontier `gpt-5` used for three trivial classification tasks (~38% of spend)

`application/clothing_classification_service.py:12`, `colour_extraction_service.py:12`, `attribute_extraction_service.py:11` all hardcode:

```python
MODEL_NAME = "gpt-5"
```

The tasks are:
- pick 1 of 6 category enums,
- pick 2 of 12 colour enums,
- fill a fixed schema of 8 enum-constrained fields.

These are the textbook use case for `gpt-5-nano`/`gpt-5-mini`. `gpt-5` costs **25× the input and 25× the output** of `gpt-5-nano` for tasks where a strict JSON schema already guarantees the output shape. The schema, not the model's intelligence, is doing most of the work.

### W3 — No `reasoning.effort` set → GPT-5 defaults to medium reasoning

Confirmed by grep: `reasoning`, `effort`, `verbosity`, `max_output_tokens` appear **nowhere** in `src/`.

`gpt-5` is a reasoning model. With no `reasoning: {"effort": "minimal"}`, every one of these calls burns hidden reasoning tokens — billed at the **$10/1M output rate** — to decide whether a t-shirt is a top. Reasoning tokens are the dominant output cost here, typically 800–1400 tokens against a ~200-token JSON answer. **This alone is roughly 70–80% of the text-call cost.**

### W4 — Three separate calls that each re-upload the same image

`openai_vision.py:186-210` and `classification/openai_adapter.py:104-130` build an identical `_vision_input` / `_data_url` payload from the same bytes.

Category, colour, and attributes are all derivable from one look at one garment. Three calls means 3× image input tokens, 3× reasoning warm-up, 3× latency, 3× failure surface. Merging them into one call with a combined schema removes two-thirds of the text spend before any model change.

There is also an ordering bug implied by the fan-out: `attribute_extraction` consumes `category_code` as a hint (`attribute_extraction_job.py:_category_code`), but it is queued **in parallel** with `clothing_classification`, so the hint is usually the user-supplied value or absent. Merging the calls fixes this too — the model sees category and attributes together.

### W5 — `detail: "high"` on 2048px images

`preprocessing/image_normalizer.py:13` → `target_long_edge: int = 2048`, and all three adapters default to `image_detail: "high"` (`run_worker.py:135,150,172`).

At `detail: high`, a 2048×2048 image costs **765 image-input tokens**; at `detail: low` it is a flat **85 tokens** — a 9× difference on the input side.

For picking a category from six options and a colour from twelve, 512px at `detail: low` is ample. Garment silhouette and dominant colour survive downscaling; these are not OCR or fine-texture tasks. The one field that genuinely needs resolution is `brand` (reading a logo/wordmark) — see §5.4 for the tiered approach that keeps it.

### W6 — SigLIP classifier built, tested, and then commented out

`workers/run_worker.py:334-340`

```python
# SigLIP classification is intentionally parked while we validate OpenAI
# vision accuracy.
# siglip_classifier_runner = TransformersSigLIPZeroShotCategoryRunner(...)
```

A **zero-marginal-cost** local classifier exists, has an adapter (`models/classification/siglip_adapter.py`), has a HF runner, and has passing integration tests (`tests/test_siglip_classification_ml_integration.py`). The SigLIP model is **already loaded in the same worker process** for `embedding_generation` — the weights are in memory and paid for regardless.

Routing classification through SigLIP first and escalating to OpenAI only on low confidence costs nothing extra and removes most classification calls entirely.

### W7 — Deterministic CV fallbacks are dead code in production

Both `AttributeExtractionService` and `ColourExtractionService` contain complete non-AI implementations (mask geometry for attributes, alpha-dominant colour for colours) that run **only when `extractor is None`** (`attribute_extraction_service.py:129`). In production an extractor is always injected, so this code never runs.

Colour extraction in particular does not need an LLM at all: the image is already alpha-masked, so dominant colour is a histogram over visible pixels. `_visible_geometry` already walks every pixel. Paying `gpt-5` to name a colour that `Pillow` can compute exactly is the clearest waste in the codebase.

### W8 — No caching, no idempotency on content

Jobs are deduplicated by `source_background_removal_job_id` (`AiJobService.php:874-882`), which prevents double-queuing within one upload but not re-processing of identical images. There is no content hash (e.g. SHA-256 of the cleaned artifact) keyed cache. A user re-uploading the same garment, or a retry after a transient failure, pays full price again.

Prompt caching is also unused: the developer instruction and JSON schema are identical on every call and are re-sent as fresh input tokens each time. Cached input is **10× cheaper** ($0.125 vs $1.25 on gpt-5).

### W9 — Retries re-run the model with no budget cap

`run_worker.py:300` marks failures `"retryable": True` unconditionally. A malformed-JSON or empty-response failure (`ModelUnavailableError` from `_response_json`) will be retried by the queue, re-charging the full call. There is no per-account or per-day spend ceiling anywhere in the codebase.

## 5. Recommendations

### 5.1 Make wardrobe visual generation opt-in, not automatic — saves ~$0.35 per 5 items

Highest-value change. Remove `wardrobe_item_visual_generation` from the automatic fan-out in `AiJobService.php:843` and trigger it only when the user explicitly taps "Generate a clean image".

Most users are happy with the BiRefNet cutout, which is already produced for free. Paying $0.07 per item speculatively, for a cosmetic enhancement most users never asked for, is the definition of leakage.

If it must stay automatic, at minimum switch to `gpt-image-1-mini` at `quality: "low"` (~$0.004/image, a 17× reduction).

### 5.2 Switch image generation to `gpt-image-1-mini` — 5× cheaper on output tokens

`models/openai_image.py:117-120`:

```python
model_name: str = "gpt-image-1-mini"
quality: str = "low"      # or "medium" if quality regression is visible
```

For a flat-lay catalog render of a single garment on a neutral background, `-mini` at low/medium is very likely indistinguishable. Validate on ~20 real items before committing.

### 5.3 Set `reasoning.effort: "minimal"` on every vision call — saves ~70% of text spend immediately

The single cheapest change to ship: one parameter, no architectural work, no accuracy risk for schema-constrained extraction.

In `openai_vision.py` and `classification/openai_adapter.py`, add to each `create(...)`:

```python
reasoning={"effort": "minimal"},
text={"verbosity": "low", "format": {...}},
max_output_tokens=600,
```

`max_output_tokens` also caps the blast radius of a runaway generation. Ship this first, today — it is independent of every other recommendation.

### 5.4 Merge three calls into one — saves a further ~2/3 of what remains

Replace `OpenAICategoryClassifier` + `OpenAIColourExtractor` + `OpenAIAttributeExtractor` with a single `OpenAIGarmentAnalyser` that sends the image **once** and returns one combined schema:

```json
{
  "category": {...},
  "primary_colour": {...}, "secondary_colour": {...},
  "subcategory": {...}, "material": {...}, "pattern": {...},
  "seasons": [...], "occasions": [...], "formality": {...},
  "style_tags": [...], "brand": {...},
  "review_required": false, "review_reason": null
}
```

The existing `_colour_schema()` and `_attribute_schema()` compose directly — this is mostly a merge, not new logic. Keep the three Laravel job types so the API contract and the mobile app are unchanged; have all three read from one cached analysis keyed by the artifact content hash, with the first job to run performing the call.

This also fixes the W4 ordering bug: the model now sees category and attributes in one pass.

### 5.5 Downgrade the model — `gpt-5-nano`, escalate on low confidence

With a strict JSON schema and enum-constrained fields, `gpt-5-nano` ($0.05/$0.40) handles this task class well. Recommended tiering:

1. **SigLIP (local, $0)** → category + embedding. Already loaded in-process.
2. **Deterministic CV ($0)** → primary/secondary colour from the alpha-masked histogram (W7).
3. **`gpt-5-nano`, `detail: low`** → subcategory, material, pattern, seasons, occasions, formality, style tags.
4. **`gpt-5-mini`, `detail: high`** → escalate only when step 1 or 3 returns confidence below `min_confidence` (0.6), or when `brand` detection is requested. This is the only step that needs resolution, and it should run on a minority of items.

The existing `AttributeExtractionRule.min_confidence` and the `review_required` flag give you the escalation trigger for free.

### 5.6 Drop `detail` to `"low"` and stop sending 2048px images

Change the three `*_IMAGE_DETAIL` defaults in `run_worker.py` from `"high"` to `"low"`, and downscale the artifact to ~512px long edge before base64-encoding it in `_data_url`. 765 → 85 image tokens, and a much smaller HTTP body.

Keep `detail: "high"` only on the escalation tier from §5.5 where brand/logo reading is actually needed.

### 5.7 Use the Batch API for non-interactive work — 50% off

Attribute extraction and wardrobe visual generation are not latency-critical; the mobile app already polls job status. Routing them through the Batch API halves the price of whatever remains after the changes above.

### 5.8 Add a content-hash cache and a spend ceiling

- Key results on `sha256(cleaned_artifact_bytes) + processing_version`. Re-uploads, retries, and duplicate garments become free.
- Move the static developer instruction + JSON schema to the front of the prompt so OpenAI prompt caching can hit them (10× cheaper on the cached prefix).
- Add a per-account daily spend cap and stop marking every failure `retryable: True` unconditionally (`run_worker.py:300`) — a deterministic schema-validation failure will never succeed on retry, and re-running it just burns money.
- Log `response.usage` (input/cached/output/reasoning tokens) on every call into `resource_metrics`, which already exists on every result payload. **You currently cannot attribute spend per job type** — fix this first so the savings are measurable.

## 6. Projected cost per item

| Stage | Per item | Per 5 items | Cut |
|---|---|---|---|
| **Today** (3× gpt-5 high + gpt-image-1 medium) | $0.114 | $0.57 | — |
| \+ §5.3 `reasoning: minimal` only | $0.084 | $0.42 | 26% |
| \+ §5.1 visual generation opt-in | $0.014 | $0.07 | 88% |
| \+ §5.4 merge to one call | $0.006 | $0.03 | 95% |
| \+ §5.5/5.6 nano + SigLIP + detail:low | $0.0008 | $0.004 | 99% |

Even stopping after §5.1 and §5.3 — a few hours of work, no architectural change — takes a 5-image upload from **$0.57 to about $0.07**.

---

## 7. Suggested order of work

1. **§5.3** `reasoning.effort: "minimal"` + `max_output_tokens` — one line per adapter, ship today.
2. **§5.8** log `response.usage` into `resource_metrics` — so you can measure everything that follows.
3. **§5.1** make wardrobe visual generation opt-in — biggest single saving, product decision required.
4. **§5.6** `detail: "low"` + 512px downscale.
5. **§5.4** merge the three vision calls into one analyser.
6. **§5.5** SigLIP-first tiering + deterministic colour; `gpt-5-nano` for the rest.
7. **§5.2 / §5.7 / §5.8** image model downgrade, Batch API, content-hash cache.
